     1→# 🪙 Budget King BD — Rewards System
     2→
     3→The rewards system should be designed as a **ledger-based system**, not simply a `coin_balance` field.
     4→
     5→The basic flow:
     6→
     7→```text
     8→Eligible Order
     9→      ↓
    10→Calculate Coins
    11→      ↓
    12→Create Coin Transaction
    13→      ↓
    14→Customer Balance
    15→      ↓
    16→Redeem Coins
    17→      ↓
    18→Receive Voucher
    19→      ↓
    20→Use Voucher on Order
    21→```
    22→
    23→And importantly:
    24→
    25→```text
    26→Cancel / Return
    27→      ↓
    28→Reverse Previously Awarded Coins
    29→```
    30→

    33→# 1. 🪙 Coin earning rules
    34→
    35→Your current concept is:
    36→
    37→> **Spend ৳2,000 → receive 2,000 coins.**
    38→
    39→I recommend making this **admin-configurable**, rather than hard-coding it.
    40→
    41→### Example rule
    42→
    43→```text
    44→Minimum eligible purchase: ৳2,000
    45→Coins awarded:             2,000
    46→```
    47→
    48→Later Admin can change it to:
    49→
    50→```text
    51→৳1,000 → 500 coins
    52→৳2,000 → 1,500 coins
    53→৳5,000 → 5,000 coins
    54→```
    55→
    56→without changing application code.

    60→# 2. What amount qualifies?
    61→
    62→You need to define whether the reward is based on:
    63→
    64→```text
    65→Product subtotal
    66→```
    67→
    68→or:
    69→
    70→```text
    71→Subtotal + delivery
    72→```
    73→
    74→or:
    75→
    76→```text
    77→Final amount after voucher
    78→```
    79→
    80→### I recommend:
    81→
    82→**Eligible purchase amount = merchandise subtotal after discounts, excluding delivery charges.**
    83→
    84→Example:
    85→
    86→```text
    87→Products             ৳2,200
    88→Voucher              -৳100
    89→Delivery                ৳80
    90→---------------------------
    91→Customer pays        ৳2,180
    92→```
    93→
    94→Eligible amount:
    95→
    96→```text
    97→৳2,100
    98→```
    99→
   100→if the voucher applies to merchandise.
   101→
   102→So the customer qualifies for the ৳2,000 reward.
   103→
   104→Delivery should not generate coins.
   105→

   108→# 3. When should coins be awarded?
   109→
   110→**After successful delivery.**
   111→
   112→Not when:
   113→
   114→* Cart is created
   115→* Checkout begins
   116→* Order is placed
   117→* Order is confirmed
   118→
   119→Recommended:
   120→
   121→```text
   122→ORDER
   123→  ↓
   124→CONFIRMED
   125→  ↓
   126→SHIPPED
   127→  ↓
   128→DELIVERED
   129→  ↓
   130→Reward eligibility checked
   131→  ↓
   132→Coins awarded
   133→```
   134→
   135→This protects against COD abuse.

   171→# 5. What happens with ৳4,000?
   172→
   173→This is something you should decide now.
   174→
   175→There are two models.
   176→
   177→### Model A — Threshold reward
   178→
   179→```text
   180→৳2,000+ → 2,000 coins
   181→```
   182→
   183→Whether ৳2,100 or ৳3,900, the customer gets 2,000.
   184→
   185→### Model B — Proportional reward
   186→
   187→```text
   188→৳2,000 → 2,000 coins
   189→৳4,000 → 4,000 coins
   190→৳6,000 → 6,000 coins
   191→```
   192→
   193→I recommend **Model B** if your intention is essentially:
   194→
   195→> 1 taka eligible spending = 1 coin.
   196→
   197→Then the rule becomes much easier to understand.
   198→
   199→But if you specifically want **fixed rewards per threshold**, use Model A.
   200→
   201→Your database should support either.

   268→├── transaction_type

   275→
   276→Example:
   277→

   285→
   286→```text id="qv9y3j"

   313→
   314→# 9. Never delete coin transactions
   315→
   316→Suppose:
   317→
   318→```text id="h9m7p4"
   319→+2,000 EARNED
   320→```
   321→
   322→Then the order is returned.
   323→
   324→Don't delete the original transaction.
   325→
   326→Create:
   327→
   328→```text id="q0k5xm"
   329→-2,000 RETURN_REVERSAL
   330→```
   331→
   332→So your history remains:
   333→
   334→```text id="g3l9k1"
   335→+2,000 EARNED
   336→-2,000 RETURN_REVERSAL
   337→----------------------
   338→0
   339→```
   340→
   341→This is much safer for auditing.
   342→
   343→**Analogy:** A bank doesn't erase yesterday's deposit when you withdraw money; it records another transaction.

   398→# 12. FIFO redemption
   399→
   400→If different coin batches have different expiration dates, use **FIFO/earliest-expiry-first** logic.
   401→
   402→Example:
   403→
   404→```text id="2a9s4k"
   405→Batch A: 2,000 coins → expires Jan 1
   406→Batch B: 3,000 coins → expires Apr 1
   407→```
   408→
   409→Customer redeems:
   410→
   411→```text id="c8x6mn"
   412→2,000 coins
   413→```
   414→
   415→Consume:
   416→
   417→```text id="o8g3zy"
   418→Batch A first
   419→```
   420→
   421→This prevents older coins from unnecessarily expiring while newer coins are spent.

   747→# 24. What if the customer already spent the coins?
   748→
   749→This is important.
   750→
   751→Customer earns:
   752→
   753→```text id="4q5m7s"
   754→+2,000
   755→```
   756→
   757→Then immediately redeems:
   758→
   759→```text id="7x2c9a"
   760→-2,000
   761→```
   762→
   763→Now their coin balance is zero.
   764→
   765→Later the original order is returned.
   766→
   767→You need a policy.
   768→
   769→I recommend:
   770→
   771→### Allow balance to become negative.
   772→
   773→Example:
   774→
   775→```text id="5s8m2q"
   776→Reward reversal:
   777→-2,000
   778→
   779→Current balance:
   780→-2,000
   781→```
   782→
   783→Then future earned coins first offset the negative balance.
   784→
   785→This prevents customers from keeping rewards after returning the purchase.

   849→Then the system should record the relationship:

   855→       ↓
   856→Voucher
   857→       ↓

  1118→# 35. Final design decisions
  1119→
  1120→### 🪙 Coins
  1121→
  1122→* Ledger-based
  1123→* Admin-configurable earning rules
  1124→* Award after delivery
  1125→* Delivery fee doesn't earn coins
  1126→* Support expiration
  1127→* Earliest-expiring coins consumed first
  1128→* Never delete transactions
  1129→* Reversals are new transactions
  1130→* Negative balances allowed for legitimate reward reversals
  1131→
  1132→### 🎟️ Vouchers
  1133→
  1134→* Admin-configurable
  1135→* Fixed or percentage discounts
  1136→* Configurable coin cost
  1137→* Optional minimum order
  1138→* Optional maximum discount
  1139→* Expiration
  1140→* One-time use
  1141→* User-specific
  1142→* Atomic redemption
  1143→
  1144→### 🔄 Returns/cancellations
  1145→
  1146→* No reward if order never reaches eligibility
  1147→* Reverse earned coins after qualifying order is returned
  1148→* Partial returns recalculate/reverse the excess reward
  1149→* Unused reward voucher can be cancelled if its qualifying order is fully returned
  1150→* Already-used vouchers aren't retroactively rewritten; the coin ledger handles the resulting adjustment
  1151→
  1152→### 🔐 Security
  1153→
  1154→```text
  1155→Customer
  1156→   ↓
  1157→Can READ own rewards
  1158→   ↓
  1159→Can REQUEST redemption
  1160→   ↓
  1161→Server validates
  1162→   ↓
  1163→Atomic transaction
  1164→   ↓
  1165→Coin deduction + voucher creation
  1166→```
  1167→
  1168→**The critical rule is that coins and vouchers are financial-like assets even though they aren't real currency. Treat them with the same accounting discipline as money: immutable ledger entries, atomic operations, clear reversals, and complete auditability.**
  1169→
  1170→
  1171→# 🗄️ Budget King BD — Database Design Plan
  1172→
  1173→For the first version, I would design the Supabase PostgreSQL database around **10–14 core tables**, with a few supporting tables for variants, groups, rewards, and auditing.
  1174→
  1175→The most important principle: **don't store derived business data when it can be calculated safely from authoritative records.** For example, coin balance should come from a transaction ledger rather than being blindly incremented in multiple places.
